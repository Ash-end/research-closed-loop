# Localize a real research problem

Turn observations into a testable problem before naming a new model. When the user supplies counts and asks for analysis, calculate and interpret them directly. A design-only request does not authorize bulk data processing. Read-only checks of actual material stay within the relevant request scope; state sources and metric definitions.

## Procedure

1. Identify the affected task, system version, setting, and practical cost. Replace “poor performance” with a measurable discrepancy and a defensible reference.
2. Define metric, unit, numerator, denominator, sampling unit, threshold, and time window. Stratify by factors relevant to the anomaly, such as size, population, time, domain, or difficulty; retain overall results to avoid presenting a selected subgroup as the whole population.
3. Examine error composition, within-group error rate, sample size, and practical loss together. When appropriate, report effect size and justified uncertainty. A group contributing 80% of errors does not imply an 80% error rate or the highest risk.
4. Check metric code, labels, missingness, near-duplicates, preprocessing differences, and system faults. An unchecked anomaly remains provisional, not a demonstrated algorithmic bottleneck.
5. Formulate: “Under X, relative to Y, metric Z differs by D (source/uncertainty), producing cost C; cause H is unknown.” Missing values remain to be measured. If the problem is unsupported, recommend measurement repair or stopping.

For a 32×32 cutoff, distinguish original versus resized coordinates and side-length versus area. Example thresholds and percentages are illustrative unless project evidence supports them.

## Deliverable

Provide the problem statement, stratified evidence or measurement plan, presence/absence boundaries, unsupported mechanism conclusions, and the cheapest useful check. For saved output, adapt the [problem card](assets/problem-card.md) and reuse project records.

This is ordinary research, not competition coaching. Diagnosis does not authorize code modification, training, paid services, or unrelated project scanning. Theory can start from propositions and assumptions. With only a topic, define a provisional task and operational measures, then plan data acquisition/annotation and measurement; pain point, cause, and novelty remain unverified.
